# Key findings

[← Back to the project README](../README.md)

The non-obvious things we learned deploying an African-language speech model to a Raspberry Pi 4 and Pi 5. Each item links to the page with the evidence. Single-run measurements are marked as such; see [Benchmarks](benchmarks.md) for why that matters.

## Model deployment

1. **"Edge-ready" on a model card does not mean an edge-ready download.** The Hugging Face repo for Sunflower-Gemma4-E2B contains only a 10.2 GB BF16 checkpoint: no GGUF, no pre-quantized file. We converted and quantized it ourselves ([Part 1](01-text-model.md)). Q4_K_M took it from 10.21 GB to 3.42 GB (66.5% smaller) and gave a near-identical answer to the F16 version on one simple knowledge question ("transform" vs "convert" the only difference). That is one data point, not a quality evaluation.
2. **Architecture decides the toolchain before size does.** Sunbird's NLLB translation model cannot become a GGUF at all (it is encoder-decoder; llama.cpp converts decoder-only models). Check the architecture first ([alternatives](limitations.md#alternatives-considered)).
3. **Audio input needs a second file and one flag.** llama.cpp loads Gemma 4's audio encoder as a separate ~1 GB "mmproj" GGUF, and the model's chat template needs `--jinja` ([Part 2](02-audio-input.md)). llama.cpp itself labels audio input "experimental".
4. **Measure RAM, don't add up file sizes.** Summing file sizes suggested ~4.5 GB for text model plus audio encoder; sampling `free -m` during a real run showed system memory in use peaking at **~2.6 GB** (about 0.75 GB of which was the idle baseline) ([Benchmarks](benchmarks.md)).
5. **Speech accuracy varies enormously by language.** From the model card: word error 0.15 for English and 0.16 for Swahili, but about 0.50 for Luganda and Runyankole, over 1.0 for the worst ([Part 2](02-audio-input.md#which-languages-does-audio-input-cover)). Those are for the full-precision model; the effect of 4-bit quantization on them has not been measured.

## Documentation vs reality

6. **A model card's example code may not exist.** `Sunbird/tts-vits-lug`'s card calls a class that is absent from the linked repository. The checkpoint, `config.json` and `vocab.txt` on Hugging Face were enough to reverse-engineer a working CPU path ([Part 3](03-text-to-speech.md)).
7. **Old research code plus new Python breaks in subtle ways.** A compiled Cython extension imported fine on Python 3.11 and failed with `ModuleNotFoundError` on the Pi's Python 3.13; loading the `.so` by file path fixed it ([Part 3](03-text-to-speech.md)).
8. **Upstream gaps are real blockers.** Orpheus-3B text-to-speech was ruled out because llama.cpp's SNAC support is an unmerged draft with unresolved CPU performance problems ([Part 3](03-text-to-speech.md)).
9. **Vendor driver scripts age badly.** The display maker's install script (its repository references a 2017-era OS) is reported by open issues to fail on current Raspberry Pi OS; a built-in kernel overlay (`piscreen`) did the job with one config line ([Part 5](05-touchscreen-device.md)).

## Hardware

10. **The Pi 4's headphone jack cannot record.** `arecord -l` listed no capture devices until a USB microphone was added ([Part 4](04-live-audio-demo.md)). A headset's microphone plugged into that jack is simply unused.
11. **A cheap USB microphone at 100% gain was noisy; 62% was clean** ([Part 4](04-live-audio-demo.md)).
12. **Touch can fail in hardware while everything in software looks fine.** The driver loaded cleanly and reported a touch device, yet produced zero events, even on a rebuilt-from-scratch configuration. A second screen worked immediately on the same configuration ([Part 5](05-touchscreen-device.md)).
13. **A mirrored touchscreen is fixed at the touch layer, not by rotating the display.** The overlay's `rotate` setting affects only the display, and a rotation cannot cancel a single-axis mirror. The overlay's own `invy` option killed touch events here; a libinput calibration matrix applied via a udev rule worked, but only took effect after a reboot ([Part 5](05-touchscreen-device.md)).
14. **Input device numbers move between boots** (`event4` one boot, `event5` the next). Match devices by a stable path, not their number ([Part 5](05-touchscreen-device.md)).

## Software on a touchscreen

15. **Drop-down menus do not work reliably with touch under Wayland/XWayland.** Tk popup menus are separate windows; taps opened them but selections were not captured. An in-app full-screen picker fixed it ([Part 5](05-touchscreen-device.md)).
16. **Separate "transcribe" and "translate" steps** cost about 20 s extra on the Pi but give a transcript to display and check (measured with 5 s recordings: median ~78 s and ~21 s; the earlier ~30 s and ~18 s figures came from a short clip and a short sentence, and the first call after a cold start takes ~150 s to listen. [Part 6](06-fast-pipeline.md) shows that keeping models loaded and using smaller specialist models cuts this a lot) ([Part 5](05-touchscreen-device.md)).

## Alternative runtime

17. **Google's LiteRT-LM converted the same checkpoint but was a worse fit.** The output was 5.07 GB vs 3.42 GB for GGUF, conversion needed an undocumented flag, the chat template failed in its template engine, and a repeat attempt ran out of disk (our estimate from the intermediate file sizes is 35–40 GB needed at peak) ([LiteRT-LM evaluation](litert-lm-evaluation.md)).

## Measurement caveats

18. **Edge timings are noisy.** Identical MMS-TTS runs varied by about 70% (5.0–8.6 s). Treat single numbers as order-of-magnitude ([Benchmarks](benchmarks.md)). Controlled `llama-bench` runs of the language model were far steadier (±0.01–0.02 tokens/s over 3 repeats), so the large TTS spread may reflect uncontrolled conditions, but we did not test that.

## Quantization

19. **The default turned out to be the right level.** Across eight levels on 200 English→Luganda sentences, Q4_K_M showed no detectable quality loss against the unquantized model (95% interval for the chrF difference: −1.5 to +0.8) and had no broken outputs. Q3_K_M was clearly worse (−4.3), and Q2_K collapsed (chrF 28.6; 51 of 200 outputs were empty or leaked control tokens like `<|turn>`) ([Quantization comparison](quantization-sweep.md)).
20. **More precision cost speed and bought nothing measurable.** On the Pi, Q5_K_M and Q6_K generated about 20% slower than Q4_K_M, and Q8_0 about 40% slower, with quality indistinguishable from Q4_K_M ([Quantization comparison](quantization-sweep.md#speed-and-memory-on-the-raspberry-pi-4)). The sizes also bunch together: "2-bit" Q2_K is only 13% smaller than Q4_K_M.

## Moving files and rebuilding

21. **File sizes do not catch damaged copies; checksums do.** Three model files crossed a USB flash drive with exactly the right size and wrong contents (a 1 GB audio encoder, a 145 MB voice model and a 1.9 GB piece of a split model). The same drive's own copy differed from the original, so the damage happened when writing to it. A different drive delivered the same file correctly. Over home Wi-Fi a 1 GB file took 11 seconds with `rsync --checksum` ([rebuild](rebuild-from-scratch.md#files-damaged-in-transit)).
22. **A rebuild on a blank card reproduced the results.** Text, audio input, speech output and touch behaved as on the first card (generation 2.4 vs 2.3 tokens/s, encoder 1.45 vs 1.48 s). The differences were setup details: `sudo` asked for a password, Imager's "password" SSH option installs no key, and the USB microphone defaulted to 100% gain again ([rebuild](rebuild-from-scratch.md)).
23. **Ship offline voices as plain folders.** The Hugging Face cache layout relies on symbolic links, which a FAT32 drive cannot hold, and a first-run download breaks an "offline" claim. The apps now prefer `~/ml/models/mms-tts-<code>`; Swahili and Acholi were tested offline on the rebuilt Pi ([Part 3](03-text-to-speech.md)).
24. **A flash drive that mounts with *"Volume was not properly unmounted"* is a warning worth heeding.** The Pi's log said this about the drive that later proved to have damaged files; eject through Finder before unplugging, and verify anyway.

## A second pipeline and keeping models loaded

25. **Loading the model once was worth about as much as changing it.** The same Gemma model took a median **121.6 s** per spoken round trip when started afresh on every tap and **65.1 s** when kept loaded in a local server (six recorded clips, Pi 4). The cost is memory (about 4.3 GB held) and a 1–2 minute start-up ([Part 6](06-fast-pipeline.md)).
26. **Smaller specialist models were faster again.** Whisper large-v3 (fine-tuned for 51 African languages) plus NLLB-1.3B, both int8 and kept loaded, took a median **40.8 s**, about 3× faster than the first app and 1.6× faster than Gemma kept loaded, with comparable word error rates on those six clips (one speaker; not a ranking).
27. **Quantize on the Mac, not on the Pi.** Letting faster-whisper quantize its float16 file at load took 82 s to load on the Pi 4; a pre-converted int8 file (1.56 GB from the 6.2 GB original) loaded in 2.8 s. The conversion needed the original weights and pinned library versions (`transformers==4.56.2`, `protobuf`), and Sunbird's published 8-bit NLLB uses bitsandbytes, which needs a GPU.
28. **Whisper pays for a fixed 30 s window, and a window exactly as long as the clip is a trap.** Shortening the window cut transcription about 5× (Pi 4: 66–72 s to 14 s), but a 5 s window on 5 s clips made Whisper repeat the sentence on 3 of 6 clips, once looping for 300 s. A 6 s window with no timestamp tokens and no repeated 3-grams fixed it; a token cap and a repeated-sentence guard cover the rest.
29. **Measure with the input you will really use.** The README's "~30 s to listen" came from a clip about a second long; with 5 s recordings the same pipeline took ~78 s. Keep timing claims tied to the clip length.
30. **Voice synthesis cost grows with sentence length, and a per-tap process adds about 10 s.** VITS runs at roughly 3–5× the audio length on the Pi 4; a background worker saves the model load and Python start-up, not the synthesis. One in-app voice step took 53 s against 31 s standalone, and we could not explain the gap.
31. **A model that runs is not a model that speaks, and check you have the right file.** We first tested `jq/vits-tts-lug-eng-onnx` and wrongly concluded the small ONNX voice was unusable: that repository holds an IPA-phoneme model, and our character input produced noise. The Sunbird tutor app downloads a different repository, `jq/sherpa-vits-tts-lug-eng`, a character-level model that works ([Part 6](06-fast-pipeline.md#a-faster-voice-a-character-level-onnx-model)). The two look alike (same size to within 0.3 MB, same graph layout); only the token list differs. The timings first reported for the wrong model were measured on clips that were not speech.
32. **A 4 GB board runs the small models slowly and cannot hold Gemma.** On an Orange Pi Zero 2W, Whisper int8 took about 24 s per clip (5 s window) and NLLB 9–20 s per sentence, with throttling from 71 to 85 °C; Gemma Q4_K_M plus its audio encoder (4.41 GB) cannot fit in its 3.9 GB (judged by size; not attempted), and the quantizations small enough are too lossy.
33. **Streaming makes slow generation usable.** At about 2.3 tokens/s a short chat answer takes 15–20 s to finish, but with the reply streamed to the screen the first words appear after about 9 s ([Part 7](07-sunflower-chat.md)).
34. **Changing the language named in a chat's opening instruction seemed to make the next reply slow.** The first word took 25–28 s after a language switch against 8–10 s within one language, probably because the server reread the whole history; this was not verified, and the app now starts a new chat on a language change.
35. **A character-level ONNX voice synthesizes at about 2× the audio length on the Pi 4**, against 2.6–3.7× for the Sunbird VITS voices, from one 109 MB file for English and Luganda instead of about 450 MB per language. In the second app it cut the voice step's median from 9.9 s to 7.1 s, though that run was hot and the totals matched ([Part 6](06-fast-pipeline.md#a-faster-voice-a-character-level-onnx-model)).
36. **int8 is not automatically faster.** Dynamic int8 quantization of the ONNX voice made it four to five times slower on the Pi 4 (12–34 s per sentence against 3–8 s) and slower on the Mac too, for a reason we have not established: a preliminary Pi 5 run (Cortex-A76, which has int8 dot-product instructions) showed the same 3–6× slowdown, so the missing instruction on the Pi 4 is not the explanation. Whisper and NLLB have only ever been measured as int8, so we do not know whether float32 would be faster for them.
37. **Read the app's source when a model won't behave.** The recipe for the working voice (lowercase characters, no blanks, `scales = [0.667, 1.0, 0.8]`, 22050 Hz) was a few lines in the Sunbird tutor app's `tts_engine.dart`, and the download URL in `tts_model_manager.dart` showed we had the wrong repository. Both took minutes to read, after we had spent much longer guessing at input formats.
38. **Whether the specialist models beat the big model depends on the board.** On the Pi 4 Whisper + NLLB was about 1.7× faster than Gemma kept loaded (36.6–40.0 s against 63.0–66.1 s); on the Pi 5 Gemma kept loaded was about 1.5× faster (12.3–12.9 s against 17.5–20.1 s). Gemma's generation speed rose 3.2× and its prompt processing 6.7×; the CTranslate2 decoders gained about 2× ([Part 8](08-pi5-and-matched-rerun.md)).
39. **Measure the split before you tune.** Whisper's time at the app's 6 s window is 82% decoder and 18% encoder, so the window shortening that removed most of the stock cost could not remove more; at the stock 30 s window the encoder is 65%. NLLB's time is almost entirely the decoding loop at about half a second per token; its encoder is under 0.5 s ([Part 8](08-pi5-and-matched-rerun.md#where-the-time-goes-pi-5-measured-with-the-diagnosis-scripts-in-scriptsfastexperiments)).
40. **For the language-model decoders, fewer bits did help.** Loading NLLB or Whisper as float32 instead of int8 made decoding 2–4× slower on the Pi 5, because each token reads about four times as many weight bytes. This is the opposite of the ONNX voice (finding 36), whose time is convolutions, not weight reads.
41. **A beam size that looks free in isolation may not be in the pipeline.** NLLB at beam 1 was 40% faster per sentence in an isolated test on the Pi 5 (7.3 s against 11.9 s) but moved the full pipeline's translate step by only 0.6–0.9 s; on the Pi 4 it cut translation by about 19% (10.8 to 8.8 s). The same call took 11.9 s in isolation and 6.6–7.4 s inside the pipeline at beam 5, which we could not explain.
42. **Power and cooling decide whether a Pi 5 benchmark is valid.** On a 5 V / 3 A adapter without a fan the Pi 5 logged under-voltage, reached 82–86 °C and ran its Gemma setups up to 1.5× slower than with a 5 V / 5 A supply and an active cooler. Check `vcgencmd get_throttled` and `dmesg` before trusting a number.
43. **Gemma's transcripts are not repeatable; Whisper's are.** The same Gemma listener scored word error rates from 0.08 to 0.29 over runs of the same clips because it samples at temperature 0.3, while every Whisper run scored 0.06.
44. **The best quantization level on the Pi 5 is the same as on the Pi 4, but for a different reason.** Q4_K_M still has the best quality for its size, and on the Pi 5 it generates as fast as Q4_0 (7.8 tokens/s); Q4_0 reads prompts 1.7× faster on the Pi 5 (not on the Pi 4). Generation falls to 4.4 tokens/s at Q8_0, whose peak memory (7.12 GB of 8.06 GB) leaves no room for the audio encoder ([quantization comparison](quantization-sweep.md#speed-and-memory-on-the-raspberry-pi-5)).
